# 平均在线 10 万、连续 72 小时：容量与 Fly.io 成本计划

日期：2026-10-29，Asia/Shanghai。分析对象为本地 WD_Ghost 源码，不是线上部署或账单审计。未部署、未购买资源、未访问生产数据库。旧 README 和对战压测不作为当前产品容量依据。

## 决策摘要

用户确认平均在线 100,000，运行 72 小时。尚无真实停留时长、录音参与率和访问资源统计；基准假设每次停留 10 分钟、20% 访问发送一条录音、每次实际网络下载公共资源 30 MB / 100 次 GET。得到 4,320 万次访问（不是独立用户数）、864 万条录音、1.296 PB 公共资源分发。

完成下述架构改造后，初始容量候选为 **17 台自管 Fly Machines + 1 个 Managed Postgres HA 集群**，其中 12 台 API、2 台后台任务、3 台 Redis。预留 API 扩到 20 台，即自管 Machines 总数 25 台。该数量是待压测的工程预算，不是已证明的承载能力。

东京 nrt，全部运行 72 小时，基准费用约 **$2,817**；加 30% 预留约 **$3,662**，可准备 **$4,000**。重度资源访问场景约 $4,113，含预留约 $5,347，可准备 $5,500。全部金额 USD、未含税、人工、额外付费支持、活动前压测与活动后保留资源费用。公开价格核验见 [独立报价依据](fly-pricing-sources-2026-10-29.md)。

最重要的前提：公共媒体和私有录音由浏览器直接访问 Tigris，不能再由应用机器中转。Tigris 免费出站不等于请求免费，也不构成 40–80 Gbps 的容量保证，必须提前获得服务方的容量确认。

## 当前代码实际做什么

| 行为 | 源码事实 | 容量影响 |
|---|---|---|
| 对战 | `src/main.ts` 没有 `/matches` 调用；后端仍有旧路由，旧压测仍模拟对战 | 正常业务模型计零对战请求；发布前下线旧入口，避免绕过 UI 继续写入 |
| 普通角色声音评分 | `src/personal-scare.ts`、`src/microphone.ts` 在浏览器计算并保存 localStorage | 不上传原始录音，不需要语音识别/转码/GPU 服务 |
| 邀请录音回传 | `src/invitation-motion.ts`：MediaRecorder 64 kbps、5 秒、Base64 JSON 上传 | 理论音频 40 KB；预算 50 KB；当前上传因 Base64 约增加 1/3；实际编码由浏览器决定 |
| 服务端录音 | `server/store.mjs:recordAudio`：最大 512,000 bytes，每用户每日最多 20 条，存 SQLite BLOB | 512 KB 是上限，不能当平均值；重复发送同一邀请/用户受唯一键保护 |
| 播放好友录音 | `src/main.ts:openReactions`：audio preload=none，点击播放才读取；后端验证邀请人 | 不是直播，也不是 10 万条持续语音流 |
| 在线状态 | `src/main.ts` 每 15 秒 `/me`，页面可见且初始化/解锁后执行 | 全部活跃时 6,667 RPS；不可见页面不算这一负载 |
| 动画清单 | `src/cute-motions.ts` 地图页每 30 秒 `/api/motions`，挂载/回到前台也请求 | 全部地图页额外约 3,333 RPS；当前端点同步遍历读取 JSON |
| 排行榜 | 排行榜页面每 60 秒刷新，切换页面/类型也请求 | 10% 用户在排行榜时约 167 RPS；与地图页比例互斥 |
| 其他操作 | session、onboard、select、invites、respond、gifts、story、events、reactions/read | 按真实交互压测，不用对战替代 |

当前 `/me` 每次除鉴权外，还查询玩家、daily、反应聚合、最近 30 条反应、progress、首次邀请。一次无录音的新玩家响应实测 294 bytes；用合成的 30 条反应构建同形状响应约 7,523 bytes。这是字节测量，不是性能测试；它说明不能把历史数据多的用户当成几百字节处理。当前 API 通用 JSON 响应没有 gzip。

当前排行榜每个请求现场聚合/排名；`invites(sender_id)` 和录音限额查询所用的 `reaction_audio(player_id,created_at)` 缺少对应索引；全局 analytics 同一日期/事件反复更新同一行也会成为写入热点。SQLite 同步单连接和单机磁盘无法通过简单复制机器安全横向扩容。

### 本地资源字节测量

按 `public/art/transformations/manifest.json` 的实际引用，播放器使用 entrance MP4、loop MP4、poster PNG；不能把目录里的所有旧文件、源素材和未使用的 alpha WebM 都算进每次访问。

- 40 个角色，每组当前引用资源平均 **5,817,614 bytes**，最小 2.93 MB，最大 8.08 MB。首次播放代码同时加载 entrance 和 loop，并设置 poster.src。
- 地图 40 张 WebP 动画贴图合计 **7,166,936 bytes**；`refresh()` 遍历所有角色并 new Image() 加载，不因角色处于 hidden 而跳过网络请求。完成下载和浏览器缓存命中率仍取决于实际访问。
- 邀请南瓜 PNG 为 **1,778,749 bytes**；地形 6 张合计 182,492 bytes；地图 JSON 138,160 bytes。
- 观看约 3 个不同角色：仅变身包约 17.45 MB，再加贴图、缩略图、UI 等，30 MB/访问是可解释的预算值，不是浏览器 HAR 实测值。重复访问命中本机缓存可降低成本，视频 Range/重试会增加请求。

`ASSET_ORIGIN` 仅覆盖部分角色图；变身视频、海报、motion sheet、地形、预览图仍使用相对路径，默认走应用域名。`scripts/publish-assets.mjs` 只上传旧 art manifest 所列内容，不覆盖上述全部资源。还有一个发布一致性问题：当前 Dockerfile 只把 public/art/manifest.json 拷入运行镜像的 public 目录，而 motions loader 从 public/art/motions 读取；dist 里有资源也不会被这个 loader 读取。需修复构建产物路径再做真实访问测试，不能声称现网已经加载了全部动画。

## 流量模型与敏感性

```text
访问次数 = 平均在线人数 × 活动秒数 / 每次访问秒数
         = 100,000 × 259,200 / 600 = 43,200,000
访问到达率 ≈ 166.7 次/秒
轻量通知轮询 = 100,000 / 15 ≈ 6,667 请求/秒
其余动态接口预算 = 20 次/访问 × 166.7 ≈ 3,333 请求/秒
优化后 API 稳态设计目标 ≈ 10,000 RPS；假设峰值设计目标 20,000 RPS
```

“20 次其他调用”是包含登录、角色选择、分享/响应、礼物、列表打开和录音签名等的预算，不是所有用户必定执行的调用数。公共 motions/catalog 不再反复打到业务 API。后台页面比例、用户独立性、行为相关性尚未测量。

基准录音：0.2 条/访问 × 4,320 万访问 = 864 万条，约 33.3 上传/秒。50 KB/条对应新增 432 GB（402.33 GiB），每条播放一次再产生 432 GB 下载。若每次访问都录音，数量和音频相关费用乘 5；若实际接近 512 KB 上限，存储/带宽约乘 10.24，但对象请求次数不变。

平均在线固定时，停留 5 分钟对应 8,640 万次访问，20 分钟对应 2,160 万次访问。公共资源和录音若按“每次访问”计，会随访问数变化；每 15 秒轮询总量不随停留时长变化。4,320 万访问不能等同 4,320 万独立玩家。数据库按最坏大量新玩家预留：每访问折合约 5 KB 关系数据/索引就是约 216 GB，还需邀请、进度、操作记录和维护余量；500 GB 是初始规划容量而非现有数据量测量。

## 必须先做的改造

1. **静态资源统一直出。** 发布完整版本化 manifest，包含 MP4、poster、sprites、terrain、预览图、JS/CSS/fonts；浏览器直连 Tigris 公共桶。更新 CSP 的 media-src/img-src/connect-src、CORS、WebGL 跨域、Range 和正确 MIME；确认浏览器 Network 中媒体不再通过 Fly。不要将“应用返回 302”当作完全消除应用请求。
2. **录音从 BLOB 改为私有对象。** API 鉴权并创建上传意图，签发短时直传 URL，上传完成后验证大小/类型/所属关系并幂等提交元数据；使用可重试的待确认状态和孤儿对象清理。收件人鉴权后取得短时读取 URL，禁止公开录音桶。不能为每次播放再代理音频字节。
3. **迁移到 PostgreSQL。** 异步数据库访问、PgBouncer 和全局连接池预算；保留余额/奖励/邀请响应的事务和唯一约束。补 sender/reaction/created_at 索引，用批量合成历史数据检查执行计划。迁移后不再让多个 SQLite 写副本各自记账。
4. **拆分通知与完整用户状态。** 保留 15 秒感知时延，改为小体积 inbox version/unread count，缓存热点；完整状态只在进入、状态变更或打开列表时读取，最近记录分页。轮询加入随机抖动、错误退避、隐藏页停用。基准 API 出站预算 80 KB/访问约包含 40 次轻量响应及其他响应；需实测压缩后的线上字节。
5. **公共数据和排行榜缓存。** motions/catalog 构建期生成并缓存；排行榜用增量聚合/快照，个人并列排名语义保持一致。Redis 仅存活跃状态与有限榜单/计数，不将 4,320 万玩家的完整排行榜塞进 8 GB 内存。Postgres 是账本真源，事务 outbox 驱动后台更新；不要用不可恢复的 Redis 写入替代账本。
6. **后台任务和写热点。** analytics 按时间桶/分片缓冲批量写，录音清理、排行聚合交给 worker；应用限流转共享状态，单机内存限流不能作为总额度。删除或关闭旧 matches 路由。Node 多进程/多 worker 利用每台 4 CPU。
7. **减少多余媒体请求。** 地图只加载可见区域 sprites，后续按需加载；转换大 PNG 海报、限制 preload。基准预算没有提前兑现全部节流收益，避免把尚未实施的优化当事实。

## Fly.io 机器规划与验收条件

| 角色 | 数量 | 每台/套餐 | 72h 费用 |
|---|---:|---|---:|
| API | 12 | nrt performance-4x / 8 GB | $207.15 |
| 后台 worker | 2 | nrt performance-2x / 4 GB | $17.26 |
| Redis | 3 | nrt performance-2x / 8 GB；1 主 2 副本，3 Sentinel | $35.31 |
| PostgreSQL | 1 托管 HA 集群 | MPG Performance / 8 CPU / 64 GB | $192.20 |

Redis 为自管服务，需部署和故障演练，不是购买上述机器后自动获得托管 Redis。每节点配置 10 GB 卷，3 天 $0.45；缓存可恢复，持久业务状态来自 PostgreSQL。MPG 套餐已经含 HA、备份和连接池，不能再按主从数重复乘价；官方未明确当前物理节点数，因此不虚构总物理服务器数。

12 台 API 的依据是：失去 1 台仍需每台约 909 RPS；若混合请求平均消耗不超过 2.64 ms CPU/request，则 11×4 CPU 在约 60% 利用率内可覆盖 10k RPS。这个 CPU 时间是**验收门槛而非实测结果**；延迟还受数据库、队列和网络制约。峰值 20k RPS 时预留 20 台 API（共 25 台自管 Machines）；8 台额外 API 即使整整运行 72h，也只增加约 $138.10，运行 6h 则约 $11.51。

必须用独立负载机，按 10万活跃会话、足够多历史玩家/邀请/反应记录、完整鉴权和限流压测。重点是 10k RPS 稳态、20k RPS 突发、新客 session/onboard、个人状态、邀请回传/读取、Range 请求和缓存失效。建议验收：同区域 API P95 <200 ms、P99 <500 ms、非预期限流错误率 <0.1%，数据库 CPU/连接/写延迟有余量；全球用户另测端到端延迟。单 API 节点退出、Redis 主节点故障、PG failover 时不能丢账或重复奖励。若数据库不足，应用扩容不能代替数据层重构。现有约49 RPS的旧 loopback 对战报告不满足这一验收。

提前确认 nrt/MPG 可用性、账户 Machine 配额和 Tigris 40 Gbps 稳态/80 Gbps 以上突发容量。这里没有执行这些云端确认，也没有把免费流量解释为无限带宽。

## 72 小时费用明细：基准场景

[Fly 官方单价](https://docs.fly.io/about/pricing)：东京机器使用页面 nrt 地区公式，亚太公网出站 $0.04/GB；[MPG](https://docs.fly.io/postgres) Performance $1,922/30天、存储 $0.28/GB/月；[Tigris](https://www.tigrisdata.com/pricing/) Standard $0.02/GiB/月、PUT $5/百万、GET/HEAD $0.50/百万、免费出站。[Tigris 全球分发与签名直传说明](https://www.tigrisdata.com/features/)。

| 类别 | 计算 | USD |
|---|---|---:|
| 应用/worker/Redis 服务器 | 上表17台，运行72h | 259.72 |
| 数据库计算与HA | 1922 × 3/30 | 192.20 |
| 数据库存储 | 保守按500GB全程 × 0.28 × 3/30 | 14.00 |
| Redis 持久卷 | 30GB × 0.15 × 3/30 | 0.45 |
| 对象数据存储 | 录音402.33GiB + 静态1GiB，保守按期末量全程收费 | 0.81 |
| 录音上传请求 | 864万 PUT × $5/百万 | 43.20 |
| 录音检查与播放请求 | 每条1 HEAD + 1 GET，1728万 × $0.5/百万 | 8.64 |
| CDN/全球分发读请求 | 每访问100 GET × 4320万 = 43.2亿次 | 2,160.00 |
| CDN/全球分发字节出站 | Tigris直出1.296PB公共资源及432GB录音 | 0.00 |
| Fly API 公网出站 | 80KB/访问 × 4320万 = 3456GB，× $0.04 | 138.24 |
| **合计** | 未抵扣免费额度 | **2,817.26** |
| **含30%预留** | 用于重试、Range、少量扩容等不确定性 | **3,662.44** |

CDN 在此指采用 Tigris 自带的全球分发，没有额外购买第三方 CDN；若需要另一家 CDN、地区 SLA 或商务套餐，必须加入其独立报价。缓存命中能减少回源，但到达 Tigris 的浏览器 GET 仍按请求计费；只有本机缓存未发出网络请求才从上述 GET 数里消失。视频多个 Range、HEAD、失败重试会增加请求，100/访问是建模值。签名请求本身主要在 API，验证对象额外按一次 HEAD 预算。

Tigris 存储按每日峰值计，本表把期末量当全程量是保守上界；并非声称实际费用就按这一公式。数据库 v2 按小时实际使用量收费，旧 v1 按配置量；表中500GB全程也是保守预算。网络 GB 以十进制保守估计，Tigris 存储使用 GiB。免费额度对数十亿请求影响很小，故未抵扣。活动结束仍保留数据库/录音/卷就会继续收费；不要为了省钱删除未批准删除的数据。

### 如果媒体继续由 Fly 应用出站

反事实比较：同一基准1.296PB如果全部经过东京 Fly 公网出站，单媒体流量约 **$51,840**，尚未计计算、数据库和API流量。这不是现网账单预测：当前一些旧角色图可能已直出对象存储，但新视频路径仍由应用服务。仅按3个角色的当前平均视频+海报包，4,320万访问就约754TB，对应约$30,158的Fly出站；再加当前全量sprites约310TB，又约$12,384。实际浏览器缓存和播放完成率会改变结果。

因此，扩大服务器之前先统一媒体分发路径。否则机器钱可能只有几百美元，公网流量却达到数万美元。
