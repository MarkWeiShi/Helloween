# Hourly analytics

The local dashboard runs with `node scripts/analytics-dashboard.mjs` and binds only to `127.0.0.1:8790`. It reads aggregate data from the Tokyo primary using the operator's existing Fly CLI authentication. The page refreshes every minute, with a 30-second query cache. All displayed hours use Asia/Shanghai (UTC+8).

On 2026-10-31 at 13:10:52 Beijing time, `node scripts/install-hourly-analytics.mjs` backed up the primary database to `/data/backups/before-hourly-analytics-1793423452784.sqlite` and installed hourly aggregation triggers. No application restart or image deployment was needed. SQLite persists the triggers across restarts; the local BooStore constructor also installs them for future releases. The installer is idempotent and preserves the original coverage timestamp.

`analytics_hourly` records positive deltas to the existing daily analytics table and first transitions from uninitialized to initialized. These writes share the application's transaction, so rolled-back or failed operations do not inflate counts. Hours use the database's real UTC clock internally. No new player identifiers or credentials are stored. `analytics_metadata.hourly_started_at` records the coverage boundary. Do not delete these tables or triggers during schema migrations.

Historical event hours and historical initialization hours are unavailable before this boundary and display as missing. The first instrumented hour displays a partial-coverage marker. Existing timestamps allow hourly reconstruction of new browser identities, new accounts, invitations, deduplicated invitation visits and retained recordings. Deleted records cannot be reconstructed. New identities are not hourly active UV, and accounts are not login events or concurrent sessions. Totals may exceed the sum of the instrumented hourly event counts because daily history predates hourly collection.

Verification: trigger insert/upsert/update accounting, migration idempotence, transaction rollback, historical missing values, hourly-to-total reconciliation of timestamped records, account/store/HTTP regression checks, date filtering, browser rendering and mobile overflow checks.

## IP-country grouping

The dashboard now offers `国家（按 IP 分组）`, an all-country default, country totals, and a country selector that filters hourly rows, card details and cumulative totals. Existing databases without country collection remain readable: all historical data is explicitly `未知 / 未采集`. Country totals are cumulative and do not follow the hourly date filter. A browser identity/account/invitation/retained recording is attributed to the IP country of its creation request, initialization to its transition request, and an analytics event to the request that recorded it. An existing visitor's later requests can belong to a different country. Distinct visitors and duration averages/medians must not be added across countries.

`server/country-analytics.mjs` resolves IPv4/IPv6 offline using the pinned `geoip-country` dataset (https://github.com/sapics/geoip-country); no external lookup request is sent. Database records contain country codes and existing record keys, never raw IP addresses. VPNs/proxies affect attribution. Self-selected player country, browser language, CDN country headers, and Fly server region are not used. Fly-Client-IP is trusted only when `FLY_APP_NAME` is set and the immediate peer is the local Nginx proxy. A direct Node server uses its socket peer. Any changed proxy topology needs an explicit review of this trust boundary.

Collection runs within the request's AsyncLocalStorage context. Connection-local TEMP triggers capture the same committed insert/update as the original data, preserving rollback and retry behavior. Persistent aggregate tables survive rollback to an old image; old connections do not depend on JS functions or TEMP triggers. Writes without collection remain unknown by subtracting known aggregates from original totals. Rerunning installation preserves the coverage timestamp. Call `installCountryAnalytics(db)` after optional engagement tables are created to register their insert/delete triggers too. Dwell fragments are attributed to the request that first inserts that visit/hour fragment; later cumulative updates keep that attribution.

The Fly-only release packages the offline database with the server runtime (including the dependency's data directory if the API build bundles JS), registers collection after all optional tables exist. Release verification checks the trusted client IP through each edge and per-country reconciliation against all-country totals. No historical backfill or CDN/R2 mutation is performed. Rebuild and review the pinned dataset for updates; it is not fetched at request time. The frontend application bundle is unchanged; collection adds offline lookup and SQLite trigger writes on the API, so server overhead requires measurement at the intended load.
